7. 通過安全檢查的訂單才可進入既有物流分流。
8. 原物流分頁規則不變。
9. 所有本批訂單完成分類與移動後，才可開始拋單＋印單。
10. 拋單、印單、多頁、物流確認、既有物流操作流程原則上全部沿用，不重新設計。

## 3. 背景、目的與成功標準

### 3.1 背景

原一頁自動化主要從「等待確認」分頁開始處理訂單。

預購期間，符合預購條件的訂單已透過現有自動化移至「其他及暫存」相關分頁。

商品正式到貨後，這些訂單仍位於「其他及暫存」，已離開原本的「等待確認」入口，因此現有一般出貨自動化無法直接接管這批訂單。

目前不希望要求使用者先人工把預購單搬回「等待確認」。

### 3.2 真正目的

新增一條安全、獨立但盡量重用既有邏輯的入口：

```text
其他及暫存
→ 關鍵字篩選
→ 人工勾選
→ 解除本次預購狀態
→ 重新安全檢查
→ 一般出貨物流分流
→ 全部分頁完成
→ 既有全自動拋單＋印單
```

### 3.3 成功標準

功能完成後：

- 可以直接從「其他及暫存」處理已到貨預購訂單。
- 不需搬回「等待確認」。
- 不會把未勾選訂單帶入流程。
- 不會因原預購關鍵字再次陷入預購分流。
- 未付款／重複／備註／留言仍會重新檢查。
- 原正常每日「等待確認」流程不退化。
- 原物流分頁與拋印流程不退化。

### 3.4 排除事項

本次不是重新設計整套一頁自動化。

除非新增入口必須調整共用介面，否則不要主動改：

- 原等待確認入口。
- 原未付款判定規則。
- 原重複訂單判定規則。
- 原物流分頁規則。
- 原物流拋單步驟。
- 原物流印單步驟。
- 原 PDF／列印流程。
- 與本功能無關的既有 Bug。
- 與本功能無關的重構。

## 11. 已到貨預購的特殊規則

```text

```

不得因此跳過：

- 顧客留言

## 20. 驗收案例

### Case 1：正常已到貨預購

- 關鍵字找到正確訂單。
- 人工勾選。
- 備註／留言顯示。
- 重新檢查付款與重複。
- 正常單進物流。
- 不再次判定為預購。
- 全部移動後才拋印。

### Case 2：同頁其他預購批次

商品 A、B 同在暫存。搜尋 A：

- 只列 A 候選。
- B 不被執行。

### Case 3：未勾選候選

即使符合關鍵字但未勾選：

- 零修改。
- 零移動。
- 零發信。
- 零拋印。

### Case 4：未付款

重新檢查為未付款：

- 不得正常出貨。
- 走既有未付款流程。

### Case 5：重複／異常

重新檢查異常：

- 顯示原因。
- 不符合條件者不得出貨。

### Case 6：備註／留言

有顧客備註、商家備註或顧客留言：

- 控制板顯示內容。

### Case 7：多頁

候選分布於多頁：

- 掃描後整合。
- 執行不遺漏。
- 不只處理最後一頁。

### Case 8：混合物流

同批包含：7-11、全家、新竹宅配。

必須：

- 沿用既有分頁。
- 全部分頁完成。
- 再啟動既有拋印。

### Case 9：原流程 regression

不使用「已到貨預購」模式時：

- 原等待確認掃描不變。
- 原預購判斷不變。
- 原未付款不變。
- 原重複單不變。
- 原備註／留言不變。
- 原物流分流不變。
- 原拋印不變。

此 Case 為本 feature 的必要驗收項目。
