> **適用場景**：任何要動到 1shop 平台互動的改動之前，**強制先讀本檔**。包含勾選、拋單、印單、翻頁、分頁移動、按鈕查找、可見性判斷。
> **不處理**：UI 元件位置與自家流程設計（→ B UI 骨架）；驗收條件（→ C BDD 現行規格）；版本沿革（→ E 變更紀錄與待修）
> **前置依賴**：無。本檔是所有平台相關改動的前置。
> **共用參照**：術語與常數

## 本檔的地位（最高優先規則）

本檔是 1shop 平台行為的**唯一權威**。這些事實全部是用真實生產環境測試換來的，不是文件推導、不是合理推論。

**三條硬規則：**

1. **表內有的，照表做。** 不重新推論、不「我覺得應該是」。
2. **表內沒有的，就是不知道。** 遇到未收錄的平台行為，停下來明確回報缺口，等 Tina 用真實訂單實測確認後才動 code。**禁止用推論當事實往下寫。**
3. **新確認的事實，先寫進本檔再寫 code。** 事實入檔 → 才改實作 → 才更新 C BDD 現行規格。順序反了就會產生影子表。

> 這條紀律是踩過坑換來的：「移走後會不會遞補」曾被 AI 當成合理推論寫進計畫，實測結果與推論相反。平台行為的錯誤假設會一路污染下游所有實作。

## 二、由事實推導的工程通則

這四條是上表的直接後果，寫 code 時當守則用：

| 通則 | 依據 | 做法 |
|---|---|---|
| **可見性判斷一律用 `offsetParent === null`** | P8 | 不用 `getBoundingClientRect().width === 0`。只有真正 `display:none` 才排除 |
| **任何「需勾選才出現」的元素，一律 `waitFor` 等渲染** | P6 + P7 | 禁止一次性查詢。目前 `tryThrowAction` / `doPrintAction` 皆已改為 `waitFor`（4 秒） |
| **分批操作後主動取消該批勾選** | P4 | 用 `batchIds` 重新掃 DOM、對照訂單號**精準取消這批**，從源頭斷開累積（方法 B） |
| **逐筆勾選 ＋ 重試清殘留，不依賴全選** | P5 | 批次開始前的殘留清除跑重試 3 輪 |
| **付款狀態用「可出貨白名單」，不用「不可出貨黑名單」** | P12 | 只有「已付款／交易成功／貨到付款／超商取貨時付款」四種算可出貨，**其餘一切（含未來新增、未知字串）一律不出貨、交人工確認**。清單不保證窮盡，黑名單漏一個就是把貨寄給沒付錢的人 |
| **付款狀態一律對 P12 的已知字串精準比對** | P12 | 禁止用關鍵字模糊猜測（例如「含線上/刷卡就算成功」）。新狀態出現時先入 P12 再改判定式 |

## 三、已被推翻的錯誤假設（禁止復活）

| 錯誤假設 | 實際情況 | 教訓 |
|---|---|---|
| 訂單移走後，下方訂單會遞補上來 | 經 Tina 明確推翻 | 平台的列表行為不可用「一般網頁應該會…」推論 |
| 拋印完成後平台會自動清空勾選 | P4：仍保持勾選 | 「完成」不等於「重置」 |
| 找不到按鈕 = 按鈕不存在 | P6/P7：可能只是還沒渲染完 | 找不到先懷疑時序，不要先懷疑存在性 |
