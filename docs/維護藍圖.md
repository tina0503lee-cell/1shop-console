# 維護藍圖
<!-- 更新：2026-08-13 -->

> **適用場景**：要新增模組、退役模組、判斷架構該不該升級或重構時讀本檔。
> **不處理**：日常改 code 的交付流程（→ `CLAUDE.md` 交付閘門）；模組內容本身
> **前置依賴**：無
> **共用參照**：術語與常數

## 新增模組

1. **給號** —— 接現有最後一碼之後（目前最後為 D，下一個是 E）。**代號不回收**，退役過的號不再使用
2. **寫檔** —— 檔名 `代號_中文名.md`，開頭必須有四行：適用場景／不處理／前置依賴／共用參照
3. **放入** `docs/`
4. **在 `CLAUDE.md` 路由表對應分類加一行**（沒加這行等於模組不存在，Claude 不會知道要讀它）
5. 檢查其他模組的「不處理 →」是否該指向新模組
6. **跑下方升級觸發檢查**

## 退役模組

1. 移除檔案與 `CLAUDE.md` 路由行
2. 檢查其他模組的「不處理 →」指向是否失效
3. **代號不回收**
4. 跑升級觸發檢查

## 檔名與引用紀律

- 模組檔名 `代號_中文名.md`，**版本交給 git，檔名不帶 `_vX.X`**
- 跨檔引用寫「代號＋中文名」（如 `→ A 平台事實`），**不含路徑與副檔名** —— 這樣搬動檔案時不用回頭改一堆引用
- 外部連結（含 Notion URL）一律收在 `E 變更紀錄與待修` 的「連結索引」，不散落在其他檔案。`CLAUDE.md` 不放 URL

## 升級觸發（每次維護操作後必檢）

| 訊號 | 該做什麼 |
|---|---|
| `CLAUDE.md` 超過 2,500 字 | 把細節下移到模組。**不要硬塞** |
| 模組數達 8 個 | 路由表改為兩層（先分類、再細分） |
| 預留分類被填滿 | 檢視路由分類是否需要重新切分 |

## 重構信號

| 訊號 | 意義 |
|---|---|
| 單一模組超過 3,000 字且難以拆分 | 該模組承載太多不同性質的內容 |
| 模組數超過 10 | 路由成本高於查找成本 |
| 問題頻繁落在兩模組之間的灰色地帶 | 分類切法不符合實際問題型態 |
| 3 個以上模組的「不處理」指向同一模組 | **該模組過載**，應拆分 |

## 常駐層瘦身順序

`CLAUDE.md` 撞到 2,500 字時，按這個順序往下搬，不要憑感覺刪：

| 順序 | 可搬內容 | 搬去哪 |
|---|---|---|
| 1 | 已搬：擴充協議 | 本檔 |
| 2 | **已搬（2026-08-19）**：說明方式的 ❌/✅ 對照表（原則留在常駐層） | `D 註解與交付規範` |
| 3 | 交付閘門的「說明」欄（留動作、搬理由） | `D 註解與交付規範` |
| 4 | 路由表的「使用者在問…」欄（留分類與檔名） | 本檔 |

**永遠不可搬出常駐層的**：五條核心紀律、路由表的分類與檔名對應。這兩者一旦不是每輪必載，等於規則不存在。
